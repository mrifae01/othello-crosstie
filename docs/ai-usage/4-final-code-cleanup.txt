⏺ No, they're separate budgets. Each service creates its own ClaudeCallLimiter,
  so they share the code but not the counters.

  ┌──────────────────────────────────────────────────┬───────────┬─────────┐
  │                     Feature                      │  Per IP   │ Whole   │
  │                                                  │           │ server  │
  ├──────────────────────────────────────────────────┼───────────┼─────────┤
  │ Game Review debriefs (CoachService.ts            │ 10 per    │ 200 per │
  │ (backend/src/coach/CoachService.ts))             │ hour      │  hour   │
  ├──────────────────────────────────────────────────┼───────────┼─────────┤
  │ Practice "Explain why" (ExplainService.ts        │ 20 per 10 │ 600 per │
  │ (backend/src/coach/ExplainService.ts))           │  minutes  │  hour   │
  └──────────────────────────────────────────────────┴───────────┴─────────┘

  So a player could use 10 debriefs and still have their full Explain why
  budget, and the other way round.

  Only new Claude calls count against either limit. Reopening a debrief that's
  already saved, or asking Explain why about a position that's already cached
  (including one another player asked about), is free.

  The one thing they do share is the cooldown. If either feature hits an account
  error (such as no credit or a bad key) or a temporary error (such as an
  overload), pauseAfter turns off both features for the cooldown period. That's
  intentional, because both calls use the same API key.

  If you'd rather have one combined budget for all Claude calls, I can create a
  single limiter in server.ts and pass it to both services. It's a small change.

  ---

  Backend

  Quality: 8/10

  What's strong:
  - The server is the only authority on the rules.
  - Each game's operations run one at a time; the database write happens before
    the in-memory cache or the broadcast changes.
  - Multi-step writes use transactions, and every tournament write holds a row
    lock on that tournament.
  - Restarts recover cleanly: unfinished analysis is re-queued, missed
    tournament results are re-fed and orphaned games are ended on boot.
  - Error codes are typed and consistent across REST and sockets.
  - The AI is grounded: the engine decides what's right, Claude only explains a
    fact sheet, and anything naming a square the facts don't is dropped.

  What costs points:
  - No automated backend tests. npm test skips the backend. smoke.ts is good,
    but it needs a running server, so nothing covers GameService,
    TournamentService or parseLine in CI.
  - The two Claude calls are copy-pasted. writeDebrief in CoachService.ts:139
    (backend/src/coach/CoachService.ts#L139) and writeExplanation in
    explain.ts:63 (backend/src/coach/explain.ts#L63) repeat the same call, error
    mapping and stop-reason check.
  - Request validation is hand-written. routes.ts (backend/src/http/routes.ts)
    has ~100 lines of parseX helpers, while zod is already a dependency.
  - Unknown /api paths return 400, but your deviation log (B2) says 404.

  Scalability: 5.5/10

  All of these are fine at take-home scale. They're the honest ceiling a
  reviewer will ask about, so they belong in the roadmap more than in code
  changes now.

  1. The design only works as a single process. Several things live in one
     server's memory:
     - the game cache
     - each game's lock
     - the analysis queue
     - the coach's in-flight dedupe, the rate limiters and the Explain why cache

     A second instance would split the socket rooms and break the locking. The
     path forward is the Socket.IO Redis adapter, database row locks or version
     checks instead of the in-memory lock, and a Postgres-backed job queue for
     analysis.
  2. The game cache never evicts (GameService.ts:96
     (backend/src/game/GameService.ts#L96)). Every game loaded stays in memory
     forever. A small fix is to drop finished games once analysis completes.
  3. Analysis runs on the main thread, one game at a time. Each move analysed
     can block the server for up to 0.4 s, and when a tournament round ends, 4
     games queue for up to ~25 s each. The fix is a worker_threads pool.
  4. Every game-state broadcast queries the tournament tables.
     TournamentService's listener runs matchForGame on every finished-state
     emit, including the analysis status changes, so each game costs about 3
     extra queries.
  5. Tournament pages poll every 5 s per viewer, and each poll runs 3 queries.
     This won't hold at world-tournament scale; a tournament socket room would.

  Organization: 7/10

  What's strong: the layering is clear (routes → services → repos, plus a socket
  layer), and each service owns one concern.

  What costs points:
  - GameError lives in GameService.ts, but 6 files import it, including the
    coach and tournament code. It's an app-wide error type and should have its
    own errors.ts.
  - explain.ts imports CoachCallError and failureKind from CoachService.ts. The
    shared Claude plumbing belongs in something like coach/claude.ts, which
    would also fix the duplication above.
  - isValidGameId is also used for tournament ids. It's really just a UUID
    check, so a generic isUuid would be clearer.
  - routes.ts (331 lines) mixes validation helpers with every route. Splitting
    it into games, tournaments, accounts and coach routers would scale better.

  New file, coach/claude.ts (backend/src/coach/claude.ts). A Claude class is now
  the one place that talks to the Anthropic API:
  - It owns the client, the model, the pause after failures and the timeout and
    retry settings.
  - claude.parse({ system, user, schema, maxTokens, label, unusableMessage })
    makes one call and returns typed { output, model, usage }. Claude's output
    is typed from the zod schema.
  - It checks whether the coach is enabled, sorts failures into account or
    temporary errors, and handles a bad stop_reason in one place.

  CoachService.ts (backend/src/coach/CoachService.ts) went from ~190 to ~115
  lines. It no longer creates or manages the Claude client. writeDebrief is now
  a short function over claude.parse that keeps the moment grounding.

  explain.ts (backend/src/coach/explain.ts) no longer imports from CoachService.
  writeExplanation is also a short function over claude.parse that keeps the
  check for squares the facts don't mention.

  ExplainService.ts (backend/src/coach/ExplainService.ts) now depends on Claude,
  not on the debrief service. The coach.claude and coach.pauseAfter() calls
  into CoachService are gone.

  server.ts (backend/src/server.ts) creates one Claude and passes it to both
  services. A failure in either feature still pauses both, and that's now
  explicit in one place instead of spread across two services.

  Removed:
