  ## Decisions already made (don't revisit them)
  - Bot levels: **Easy / Medium / Hard**. The bot must be beatable.
  - **Practice games are not saved.** No backend, no login, no DB. The practice
  page does not use `GameClient`, so it also works in mock mode.
  - **Grading is engine-only**, reusing `classify` and motifs, so a grade means
  exactly what it means in Review. No LLM call per move.
  - **The eval bar is a toggle, off by default**, remembered per browser in
  localStorage (wrap every read and write in try/catch).
  - **The bot never blocks the player.** There is no "Continue" button in the
  normal flow. Details below.

  ## What the player experiences
  1. From Learn they choose a level and a color (Black / White / Random). If
  they play White, the bot moves first.
  2. On their turn, a Web Worker scores every legal move in the background.
  They can click **Hint** (the idea behind the best move) or **Show best** (a
  ring on the best square).
  3. They move. The grade appears in the coach bubble straight away, e.g. "c4
  is a mistake: gives away about 6 discs. f5 was best. This move opens a corner
  for the opponent."
  4. The bot replies **on its own** after a delay that depends on t

  - **Planned design:** `POST /api/coach/explain` with `{ moves, ply }`. The
  server replays the moves (rejecting illegal ones), searches, then calls
  `gradeMove`, `buildMoveFacts` and Claude, and checks the squares Claude names

    - `GET /api/coach` returns `{ enabled }` so the button can be hidden;
    - an in-memory cache keyed by position + move + prompt version;

  - **`gradeMove` refactor:** the existing `analyze` tests pass unchanged.
  - **`bot`:**
    - it always returns a legal move;
    - Hard always plays the engine's best move;

  - **`practice` reducer:**

  The one real problem: grades may not match between browser and server

  Practice grades moves in the browser with ANALYSIS_SEARCH_OPTIONS, which
  includes a 400 ms time budget. How deep the search gets therefore depends on
  the machine. A fast laptop might reach depth 8 while a Render instance only
  reaches depth 6. If the server grades the same move again, a move near a
  threshold can come out as a "mistake" in the bubble and an "inaccuracy" in the
  explanation.

  There are two ways to handle it:
  - Server re-grades, and its grade wins (recommended). The client sends only {
    moves, ply }, as your original plan says. The response carries the server's
    grade, and the bubble swaps to it if it differs. Because the client sends
    only move squares, there's no free text to inject. Mismatches should be rare
    and only at class boundaries.
  - Client sends its grade. The explanation would always match what's on screen,
    and it saves about 0.4 s of server CPU. But the server would be explaining
    numbers it hasn't checked. It's defensible, since the input is only numbers
    and squares validated by zod and a fake grade only misleads the sender, but
    it weakens the "the engine decides" story.

  How it works:
  - Server: POST /api/coach/explain takes { moves, ply }. It rebuilds each move
    from its two fields, rejects lines that aren't legal games (bad passes
    included), then grades with the same search and gradeMove as Review. It
    builds the fact sheet (buildMoveFacts), calls Claude, and rejects any answer
    that names a square not in the facts.
    - Results are cached in memory, and simultaneous identical requests share
      one call.
    - Rate limits apply to new explanations: 20 per IP per 10 minutes and 600
      per hour server-wide.
    - GET /api/coach returns whether the coach is on; when it's off, the button
      is hidden.

    alternative"). Mistakes are explained against the engine's best move, and
    forced moves as the only legal option.
  - Frontend: Explain why pauses a pending bot reply, like Hint. The explanation

  removed, one turn at a time. All 89 tests and the typechecks pass (the
  command's exit code 1 is just the zero-error grep -c count).

  In the browser, I played three turns, took back two, then went forward with →
  and with the button. Each step brought back my move and the bot's reply with
  their grades, and the Forward button disappeared once the line was complete.
  Taking back and playing a different move removed it too.

  How it behaves:
  - One turn per step: your move, then the bot's reply and any passes up to your
    next move. It mirrors Take back, so you always land on your own turn.
  - If you took back before the bot replied, Forward restores just your move,
    and the bot then replies as usual.
  - Grades come back with the moves. A move you'd already had explained shows
    its AI explanation again without a new API call.
  - Playing a different move discards the forward history, as chess.com does.
  - The button appears only when there is something to replay.

  In the code, the reducer keeps what Take back removed in a new redo list (plus
  those moves' grades) and a new forward action replays it. The hook exposes
  forward, and the page gets the button, a new RedoIcon and the → shortcut.
