⏺ I've read the codebase, and my ideas are below. Your placeholders already mark
  where AI should go: CoachBubble says "the AI coach will replace coachLine",
  and the Learn and Play pages have "Coming soon" slots.

  What the codebase already gives you

  The hard part is done. analyze.ts (shared/src/engine/analyze.ts) produces, for
  every move:
  - the loss in discs and a classification (best, good, mistake, blunder…);
  - the top 3 candidate moves and whether the eval is exact;
  - motifs such as missed corner or X-square.

  These are stored in Postgres per ply. /api/me/games exists and its comment
  calls it "the seed of cross-game coaching".

  The main design principle I'd propose: the engine decides what is correct and
  Claude explains it. LLMs are poor at calculating Othello positions and will
  confidently make up lines. So Claude never evaluates a position. It gets the
  engine's numbers and turns them into teaching. That's also a good interview
  answer to "how do you stop it hallucinating?"

  Ideas, ranked by value per hour

  1. Coach's debrief (AI game review): my top pick
  - Once analysis is done, make one Claude call per game, from one player's
    point of view.
  - Input: a compact list of plies, the summary, and the motifs.
  - Output: structured JSON, which the code checks before using:
    - the 3 moments where the game turned, each with an explanation;
    - 1–2 themes ("you gave away corners through X-squares 3 times");
    - one takeaway for next game.
  - The key moments appear in the existing CoachBubble and eval graph, so the UI
    change is small.
  - The result is cached in a new coach_reviews table, keyed by (game_id,
    player, prompt_version). That controls cost and keeps a record.
  - If a response mentions a square or ply that doesn't exist in the data, the
    code drops it.

  2. "Ask the coach" about a position (tool use): the most AI-native feature
  - A chat box on the review page: "Why is e3 bad here?"
  - The backend runs a Claude tool-use loop with tools backed by your existing
    search():
    - evaluate_moves(position)
    - play_line(squares), which returns the resulting position and eval
  - Claude looks up the actual numbers before answering. This is the feature
    eothello can't copy with a template. It also has the most risk: latency,
    loop control, and cost per question.

  3. Puzzles from your own mistakes: mostly no AI needed
  - Every blunder where the best move is clearly better than the second-best is
    a ready-made puzzle, and the engine already knows the answer.
  - This fills "Practice a position" and replaces the single hard-coded
    CornerPuzzle.
  - It's deterministic and cheap. Claude could optionally write a one-line hint,
    cached like the debrief.

  4. Training plan across games: fills the "Build my plan" card
  - Skill scores (corners, edges, mobility, parity, endgame) come from code, not
    Claude. They're built from motifs and loss grouped by game phase across
    your finished games.
  - Claude only writes the plan text on top of those scores.
  - The scores need a few new features computed in shared: mobility, frontier
    discs, stable discs, parity. Note that types.ts is marked FROZEN CONTRACT,
    so adding motifs means changing the contract.

  5. Engine bot with levels: I'd skip it or keep it minimal
  eothello already has an AI opponent, so a bot isn't a differentiator. If you
  build one, it's the search with depth and noise settings, about 30 minutes,
  and it doesn't need Claude.

  How it fits the architecture

  - New module: a backend/src/coach/ folder containing:
    - CoachService, which follows the AnalysisRunner pattern;
    - prompt files with a version number and the model name.
  - Server-only key: the API key lives on the server only (ANTHROPIC_API_KEY in
    config.ts and on Render).
  - Graceful fallback: if the key isn't set, the app keeps showing today's
    template coach. This mirrors how authEnabled lets accounts be switched off.
  - Grounding: before calling Claude, compute facts in code (disc counts,
    mobility, which corners are open) so it never has to count anything itself.
  - Model: I'd check the current models and pricing in the claude-api reference
    when we implement, rather than guess now. My instinct is a Sonnet-class
    model for the debrief and a cheaper model for hints.

  What I'd do with your 2 hours

  1. ~75 minutes: the debrief (#1). It builds the foundation everything else
     reuses: the coach module, caching, grounding and the fallback.
  2. ~45 minutes: puzzles from your mistakes (#3). It closes the loop: play,
     review, then drill the moment you got wrong.
  3. Roadmap: #2 and #4 go in the roadmap, explained as extensions of the same
     CoachService and coach_reviews table.

  That tells one story: "eothello tells you that you lost. We tell you why, and
  make you practise it." If you'd rather have the most impressive AI demo, swap
  #3 for #2.

  Questions for you

  1. Who is the coaching for? Should the debrief be for the player whose seat
     you're in, both players, or also spectators? Should guests get it, or only
     signed-in accounts?
  2. When and where does it run? Automatically after analysis, or only when
     someone clicks a button? Graders running locally won't have your key, so is
     the Render deployment the main place people see AI, with the template as
     the local fallback? Or will you document "put your key in .env"?
  3. Who is the target player? Beginners, who need concepts explained, or club
     players, who want terse lines? This drives the prompt's tone.
  4. Which bet? Is the "Ask the coach" chat something you want in this build, or
     are you happy for it to be the headline roadmap item?
  5. Club angle: do you see coaching tied to clubs and tournaments (for example,
     organizers getting a debrief for every game in a bracket)? That would
     change what we store.

  How it works
  - Code decides what to discuss. coach.ts (shared/src/coach.ts) picks the

    - the engine's top 3 moves;
    - how many replies the opponent had after each option;

      exactly.

    engine is the source of truth and not to read the board itself. It returns
    structured JSON (headline, overview, strength, key moments, takeaway), which
    the SDK checks against a Zod schema.
  - Checks on the reply. Any moment that names a ply we didn't ask about, or a
    square not in its facts, is dropped and logged. That's the main guard
    against invented lines.
  - Caching. CoachService.ts (backend/src/coach/CoachService.ts) saves each
    debrief in a new coach_debriefs table (006_coach_debriefs.sql

    PROMPT_VERSION, along with token counts for tracking cost. Two people

      whether the coach is on. It never calls Claude.

      serves the cached one.
  - UI. The review page gets a "Coach's debrief" card with a Black/White toggle,

  How the fallback works
  - Shorter waits: the Claude request now times out after 30 seconds and retries
    once, instead of 120 seconds with two retries. The worst case before the
    fallback went from about 6 minutes to about 1 minute.
  - Failures are sorted in CoachService.ts (backend/src/coach/CoachService.ts):
    - Account problems (out of credit, bad or revoked key, rejected request):
      the coach pauses for 30 minutes.
    - Temporary problems (timeout, connection error, rate limit, server
      overload): the coach pauses for 2 minutes.
  - While paused, the server reports the coach as off, so reviews go straight to
    the normal engine review with no failed button click. Saved debriefs are
    still shown, because they cost nothing to read.
  - In the browser, when a request fails with "coach unavailable":
    - a toast says the AI coach isn't available and the engine review below is
      complete;
    - the "Get debrief" button is hidden;
    - the key-moment explanations disappear, and the move-by-move coach goes
      back to its template text.

    Any other kind of error still shows inline as before.
