  Tournaments plan

  Scope: what to build first

  - Format: round-robin, capped at 8 players. Everyone plays everyone, so all
    pairings can be generated when the tournament starts. There's no
    round-by-round pairing step and no waiting for a round to finish. Swiss is
    the Othello standard and the design contract lists it for Milestone 3, but
    it needs per-round pairing logic, byes and tie-break rules. Leave it for
    later.
  - An account is required to create or join. Guests can still view a tournament
    page and watch its games through the existing spectator links. Tying
    entries to accounts is most of the point of having them.
  - Lifecycle: registering → active (the creator presses Start, minimum 2
    players) → finished (every paired game is finished).
  - Standings are computed, not stored. Win = 1, draw = ½, with disc
    differential as the tie-break, all derived with SQL over games. There's no
    score column that can drift out of sync.

  Backend

  003_tournaments.sql (002 is taken by the accounts migration)
  - tournaments: id, name, created_by → accounts, status, max_players,
    created_at, started_at, finished_at
  - tournament_entries: (tournament_id, account_id) primary key, joined_at
  - games: add tournament_id (nullable FK) and round (nullable), plus an index
    on tournament_id
  - Make black_token_hash nullable. This follows from the design choice below.

  The one real design choice: how players get into a paired game. Today a seat
  token is created at create/join time and only its hash is stored, so the
  server can't hand the token to a player later. The fix is to create tournament
  games with both *_account_id columns filled in and no token hashes. A player
  then calls POST /api/tournaments/:id/games/:gameId/seat with their bearer
  token. The server checks that the account owns a seat in that game, then
  issues (or rotates) that seat's token. The game becomes active once both seats
  are claimed. The benefit is that the socket layer, the move logic and the
  leave guard stay exactly as they are.

  Tournaments plan v2: single elimination

  Format rules

  - Bracket size is the next power of two at or above the entrant count (2, 4 or
    8; the cap is 8), with 2 to 8 players. Empty slots are byes, and a player
    with a bye advances automatically.
  - Seeding is a random shuffle when the creator presses Start, placed into
    standard bracket positions (1v8, 4v5, 2v7, 3v6). Byes go to the top seeds,
    so two byes never meet in round 1. If someone drops out before Start, the
    rest still works.
  - Colors: the player from the upper slot plays Black in each match.
  - Draws: a 32–32 result can't be broken on disc count, so the players replay
    with colors swapped until someone wins. Resigning counts as a loss.
  - Finish: the tournament ends when the final is decided, and its
    winner_account_id is set.

  Schema (003_tournaments.sql)

  - tournaments: id, name, created_by → accounts, status
    (registering|active|finished), max_players (2–8), winner_account_id,
    timestamps
  - tournament_entries: (tournament_id, account_id) primary key, seed (null
    until Start), joined_at
  - tournament_matches: primary key (tournament_id, round, slot),
    black_account_id, white_account_id, current_game_id → games,
    winner_account_id, status (pending|playing|decided)
  - games: add a nullable tournament_id so a match's replays stay linked as
    history. Make black_token_hash nullable.

  At Start, every match row for the bracket is created up front. Round-1 matches
  get their players and games immediately, and later rounds fill in as winners
  advance. The next match for a winner is simply (round + 1, floor(slot / 2)),
  and even slots feed the Black seat. This makes the bracket easy to render: the
  UI only reads match rows.

  Getting players into games

  Tournament games are created as waiting, with both *_account_id columns set
  and no token hashes. POST /api/tournaments/:id/matches/:round/:slot/seat
  (account required) checks that the caller is in that match, then issues or
  rotates that player's seat token. The game becomes active once both seats are
  claimed. After that, the socket, move and resign code is unchanged.

  Two holes to close:
  1. The existing joinGame only checks status = 'waiting' AND white_token_hash
     IS NULL. Anyone holding the link could take the White seat in a tournament
     game. It must also require tournament_id IS NULL.
  2. seatFor()/sameHash must handle a null token hash (an unclaimed seat)
     without throwing.

  Advancing the bracket

  A TournamentService subscribes to GameService.onState. When a game with a
  tournament_id finishes:
  - Draw: create a replay game with colors swapped and point current_game_id at
    it.
  - Win: mark the match decided and place the winner in the next match. If both
    players for that match are now known, create its game. If this was the
    final, finish the tournament.

  All of this runs in one transaction with SELECT … FOR UPDATE on the tournament
  row. Otherwise, two semifinals finishing at the same moment could both try to
  create the final. Byes are resolved the same way at Start, so a bye into an
  existing opponent still creates that game.

  No-shows matter more in a knockout than in round-robin, because one stuck game
  blocks the whole bracket. Add POST …/matches/:round/:slot/forfeit {
  loserAccountId } for the creator. It ends the game as a resign and advances
  the other player. Clocks and automatic forfeits stay on the roadmap.

  Postgres (not your hosted database):

    joining, starting and cancelling again are all refused.

    decided are kept, and the next-round game is never created. A game result
    that arrives after the cancel is ignored, and a forfeit is refused.
  - Crash recovery: if the server dies between cancelling and ending the games,
    it ends the leftover game on the next start. Running it a second time does
    nothing.
